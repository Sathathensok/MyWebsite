Building a Portfolio in Pure HTML/CSS/JS — No Frameworks

A walkthrough of how I built this site from scratch, the design decisions behind it, animation techniques in vanilla JS, and the honest case for staying framework-free when you don't need a framework.

When I started building my portfolio, the obvious path was to reach for a popular framework — React, Vue, or one of the many site builders that promise professional results in minutes. I chose not to, and this article explains why, and what I learned building everything from scratch.

Fair disclaimer upfront: I'm not a framework fundamentalist. For the right project, React is an excellent choice. But a personal portfolio is a specific type of project with specific constraints, and I think the framework-free approach deserves a more honest evaluation than it usually gets.

Why Not a Framework?

The most honest answer is: I didn't need one. A portfolio site is a collection of mostly-static pages. There's no complex state management. No real-time data synchronisation. No reusable component library serving thousands of users.

When you add React to a project that doesn't need it, you're adding:

  • A build process and associated toolchain (Webpack, Babel, or Vite)
  • A JavaScript bundle that the browser must download and parse before rendering
  • A framework version that will need updating and could introduce breaking changes
  • An abstraction layer between you and the HTML the browser actually reads

For a portfolio that lives or dies on first impression and load speed, these are real costs. And when you remove them, you discover that plain HTML, CSS, and JavaScript are significantly more capable than their reputation suggests.

"Understanding the basics deeply is more useful than knowing a framework shallowly."

The Design System: One CSS File to Rule Them All

The entire visual language of this site lives in a single Style.css file, built around CSS custom properties (variables). This approach has a significant advantage: changing one variable updates every element that uses it throughout the entire site.

The design system is deliberately minimal. Rather than building a large component library upfront, I started with the typography and colour variables, then added components only as I needed them. This kept the CSS lean and the design cohesive.

Core Design Tokens

Two fonts: Playfair Display (display headings, editorial weight) + Plus Jakarta Sans (body, clean and readable). One accent colour: slate-teal (#0d7c8f). A six-step grey scale for backgrounds, borders, and text hierarchy. Everything else derives from these.

Animations Without a Library

This site uses four distinct animation types, all implemented in vanilla JavaScript and CSS without a single external animation library.

1. Scroll-triggered fade-ins

Every section that animates on scroll uses the Intersection Observer API, which allows the browser to notify JavaScript when an element enters the viewport — without the performance overhead of a scroll event listener. Elements get the class fade-up or fade-in in HTML, and CSS handles the actual animation with opacity and transform. The JS simply adds a visible class when the threshold is met.

Staggered animations (where multiple elements enter with slight delays) are handled by computing each element's index among its siblings and setting a data-delay attribute accordingly. The observer then uses setTimeout to apply the delay before adding the visible class.

2. Animated number counters

The statistics strip on the homepage uses a custom counter animation. It uses an easing function — specifically an exponential ease-out — to make the count feel natural rather than mechanical. The formula is straightforward: eased = 1 - Math.pow(2, -10 * progress), which produces fast initial movement that decelerates as it approaches the target.

3. Typing effect

The rotating text in the hero section cycles through an array of words using a character-by-character approach with separate speeds for typing (75ms per character) and deletion (45ms per character). A short pause at the end of each word before deletion begins makes the effect feel intentional rather than mechanical.

4. Card tilt effect

The subtle 3D tilt on project cards is calculated from the mouse position relative to the card's bounding rectangle. The tilt angle is kept small (±5 degrees) to feel elegant rather than disorienting. CSS transform-style: preserve-3d is required for this to work correctly.

Multi-Page Architecture vs. SPA

This site uses separate HTML files for each page rather than a single-page application (SPA) pattern with client-side routing. For a portfolio, this has several advantages:

  • Each page is independently cacheable by the browser
  • Search engines can crawl and index each page separately (better SEO)
  • A broken JavaScript file doesn't prevent the HTML from loading
  • No routing library required

The shared elements (header, footer, navigation) are duplicated across pages. In a larger project this would be a maintenance concern, but for a portfolio of this size, it's a pragmatic tradeoff.

The Contact Form: FormSubmit.co

The contact form on the Hire Me page uses FormSubmit.co, a free service that accepts standard HTML form submissions and forwards them to a designated email address. No backend required, no server to manage, and it handles basic spam protection.

For a portfolio contact form, this is entirely sufficient. The alternative — building a Node.js backend with email sending, form validation, and rate limiting — is not warranted for the volume of contact form submissions a personal portfolio receives.

Performance Considerations

Without a build process, performance optimisation becomes more manual. The main things I did:

  • Used Google Fonts with display=swap to prevent layout blocking
  • Used passive: true on scroll event listeners to avoid main-thread blocking
  • Used Intersection Observer instead of scroll listeners for animation triggers
  • Kept the main JavaScript file small and deferred it to the end of the body
  • Used CSS transform and opacity for animations (GPU-composited, no layout reflow)

"The fastest code is the code you didn't ship."

What I'd Do Differently for a Client Project

For a personal portfolio, this approach works well. For a client project with a team, ongoing development, and potentially complex features, I would likely make different choices:

  • A static site generator (like Eleventy or Astro) to handle the multi-page HTML duplication problem
  • A CMS if the client needs to update content without touching code
  • A component-based approach (React or similar) if the UI has genuinely complex interactive state

The right tool depends on the project's actual requirements. For this site, vanilla was right. For your project, it might not be — and that's a perfectly reasonable conclusion.
